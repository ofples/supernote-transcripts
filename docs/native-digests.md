# Save Reader selections as native Digests

Supernote Transcripts 0.16.0, MD Reader 2.2.1, and Supernote Bridge 0.6.1 provide an optional Android workflow for saving selected Reader text as a native Supernote Digest. Reader offers one **Create Digest** selection action and returns after Bridge verifies the save. A Highlight with a linked receipt hides creation and retains **Open Digest**. Bridge comments use the source notebook's path relative to `Note` without the `.note` suffix, followed by its page; Markdown sources show their vault-relative source and optional heading without inventing a page. New comments contain no Obsidian URI, while existing stored comments remain readable as saved. Ordinary Markdown reading and Digest provenance do not require the Transcripts plugin; managed transcript selections use its validated notebook/page adapter.

## Requirements and selection menu

- Obsidian and MD Reader 2.2.1 on a compatible Supernote Android device.
- Supernote Bridge for native Digest creation and opening a saved entry from a linked Reader Highlight.
- For managed transcript selections, Supernote Transcripts 0.16.0 and a matching local `.note` mirror. The adapter validates the current notebook and page identities. Hidden page chips do not remove the underlying source anchors or provenance.

On Android, Reader's selected-text inline menu offers **Create Digest**, **Highlight**, and **Copy**. If a long drag leaves the menu closed, tap inside the selected text to open it. Tapping an action may clear Android's blue selection, so Reader snapshots and validates the selected excerpt before dispatch. Automatic menu opening after a long hardware drag was not retested during the current run.

Create Digest saves a separate Reader Highlight Markdown record before the Bridge handoff. The Highlight syncs through Obsidian Sync and does not edit the source Markdown or `.note` file. Bridge performs a verified save and returns a SAVED callback while keeping Reader in front. **Open Digest** from a linked Highlight opens native Digest details; the user can tap its native **Edit** control. On first use, a standard Android permission dialog asks whether Obsidian may create Digests for the vault. Later trusted requests need no Bridge interaction. A cancelled or uncertain native save does not remove the Highlight.

## Category selection and provenance

Reader's global default is an exact native category name. If it is blank, Reader leaves category selection unset and Bridge uses its existing device-local default, falling back to native **Uncategorized** if that list is unavailable. A Transcripts source catalog can inherit the Reader default or set a source-specific category name. An explicit empty source override means **Uncategorized** and is synchronized through the Transcripts catalog; category names are portable, while native provider row IDs are device-local. Bridge refreshes the provider list and requires one exact unique name match before insertion. A missing or ambiguous category fails before the provider write and returns an actionable cancellation result to Reader.

For managed transcripts, Bridge stores notebook/page identifiers as provenance. The Digest comment shows the path relative to the local `Note` folder without `.note`, then `| Page N` (for example, `Satsang/2610 - Satsang | Page 32`). Its `supernote_bridge.note` metadata retains the full note path, page, file ID, page ID, and page ID list alongside the Obsidian source path and context. For ordinary Markdown, the comment shows the vault-relative source path without `.md` and an optional heading; it does not add a page number. New comments omit Obsidian URIs. Reader and Bridge leave the original note and source Markdown untouched.

## Saved Highlight receipts

When a Reader Highlight has a local SAVED receipt, its action menu can offer **Open Digest**. Bridge opens only the row resolved from its local SAVED ledger; an asserted ID, when present, must match. The route performs no provider write. Reader Highlights sync as Markdown, but their receipt association and native row ID stay local to the device that created them. A synced Highlight on another device may not have an **Open Digest** action there. Removing the Highlight removes its Markdown record only; it does not delete the native Digest.

Bridge preserves the original capture payload and request ID as the deduplication identity. Delivery settings are separately HMAC-bound. Reopening a verified SAVED request does not insert another Digest or move it to a newly selected category. PENDING and UNCERTAIN outcomes block retry; no-write failures return a cancellation outcome. Reader reports a save only after a verified SAVED callback or a local SAVED receipt.

## Native backlink limitation and investigation

The current Reader/Bridge workflow still does not create native Digest-to-notebook links. Static inspection of the current Knowledge 1.00.153 APK shows that its native source action reads an embedded reference from a textbox in the `.note` file, keyed by the Digest's provider `unique_identifier`. The ordinary Digest comment URL is not clickable. Existing Transcripts page chips can still open their source notebook where shown; that navigation is separate from a native Digest backlink. The APK finding is static evidence, not a live UI test.

The offline investigation has identified a reachable type-100 `TOTALPATH` object containing the embedded Digest UID. The read-only parser and in-memory exact-object append prototype pass 11 tests across three public Digest fixtures, including reachability, malformed block/tail rejection, prefix and predecessor preservation, and rejection of changed file/page identity or a non-Digest appended object. These checks validate the observed file structure and append guard conditions; they do not prove a production writer or native backlink behavior.

The investigation includes a native-created N6 before/after pair from a disposable note. A guarded hidden-anchor candidate passed native Source, but the anchor became visible after a native edit/save cycle. A minimal converted-textbox candidate also failed Source. Embedded native backlinks therefore remain parked; there is no production `.note` writer, and original notes remain unchanged. The disposable test note and Digest were removed after preserving private evidence. See the [offline reference experiment](../experiments/native-digest-reference/README.md).

The earlier local Bridge candidate was verified on a synthetic Markdown selection. Its legacy saved comment included the Obsidian link; the current formatter uses the vault-relative source and heading without a URI. Saved comments from earlier receipts continue to read back verbatim, and capture request identity is unchanged for deduplication.

## Verification status

Prior live checks were performed with the Bridge 0.6.0 debug candidate and Reader/Transcripts candidates before 2.2.1/0.16.0. They covered Quick save and return, duplicate protection, the former open-native action, cancellation and correction for a missing category, exact **Uncategorized** selection, saved receipt opening, and native editing. Those checks do not verify the current Reader menu suppression or comment formatting, nor the Bridge 0.6.1 release artifact. The 0.6.0 debug candidate shared a versionName with the previous published release but was a different artifact; installed code must be identified by its artifact hash and contents, not versionName alone.

The earlier Bridge 0.6.0 protocol/JVM checks and debug APK build passed, along with the live smoke checks above. A screenshot sample confirmed the saved Highlight mark color as RGBA `(184, 184, 184, 255)` against adjacent white `(255, 255, 255, 255)`; the mark reappeared after reopening. The original reading location, five Reader leaves, and exact 20-position map were restored; the global category is blank. The recognition queue is idle and durably paused, automatic checks are off, and no recognition ran. Cleanup removed the three test Digests with individual native Details confirmations, the fixture source/folder and three owned Highlight files, and local test requests. Three Bridge audit receipts were intentionally retained; ten earlier ledger rows and trust/preferences were unchanged. Source/global category controls were visible and Transcripts catalog logic passed core fixtures; only the exact named **Uncategorized** selection was tested live, with no nondefault native category or two-device category sync. Menu taps were tested; automatic menu opening after a long hardware drag was not retested. Native cloud sync, Partner behavior, rename handling, and cross-device receipt resolution also remain unverified. Verification of 0.16.0/2.2.1/0.6.1 is pending; see [page-link history](../PAGE_LINKS.md) for separate existing page-chip navigation evidence.
